# 公式模型压缩与提速候选验证

后续在相同存储精度下的注意力融合实验见 [公式解码注意力融合候选](2026-10-29-formula-attention-fusion.md)。

## 当前结论

保留的候选为 **FP16 存储、FP32 计算**，同时包含此前验证的投影外提。公式模型从 566.40 MiB 降到 284.16 MiB，体积约为原来的一半。

相对未经投影外提的原模型，同一时间段串行 ABBA 对照中，74 个公式的平均推理耗时减少约 16%，速度约 1.19 倍。**没有实现数倍提速。** 相对上一轮已经外提投影的 FP32 候选，本轮也没有证据证明稳定的额外大幅提速；主要新增收益是文件大小和内存。

默认模型、已安装包与 Rust 二进制均未替换。本次新增的是离线候选生成和验证工具，正常解析及其他语言加载模型不需要引入 Python 改图或量化依赖。

## 实验结果

所有候选均基于同一份、已验证投影外提的图。先安全清理内部 Identity 别名，保留图输出与可能被子图局部绑定遮蔽的别名。未改输入分辨率、词表、生成长度和文档规则。

| 候选 | 文件大小 | 74 个真实公式与原始 token 完全一致 | 处理 |
| --- | ---: | ---: | --- |
| FP16 存储、FP32 计算 | 284.16 MiB | 74/74，多轮通过 | 保留独立候选 |
| INT8 动态量化 MatMul、Gather | 341.50 MiB | 70/74 | 不接入 |
| INT8 MatMul，嵌入等其余权重 FP16 存储 | 235.22 MiB | 67/74 | 不接入 |
| 再保留词表输出层不做 INT8 | 259.39 MiB | 70/74 | 不接入 |

一致率是与原模型的结果符合程度，**不是标注语料上的识别准确率**。缺少对应标注，不能判定不同结果是改善还是退化，因此量化后出现变化的候选均未采用。

FP16 也会改变权重数值，包括极小值下溢为零，不属于无损压缩。保留候选通过的是已测输入与 PDF 的输出校验，不能据此保证任意输入都不会变化。

## 速度与内存对照

四轮独立进程按原版、候选、候选、原版运行；A1 复用紧邻实验的一次标准 worker 报告，已核对模型哈希、74 个输入对应结果、profiling 关闭、CPU arena 开启及自动线程。其余三轮使用同样设置。各进程相同短例预热，加载、文件读取与输出校验不计入推理耗时。

| 顺序 | 模型 | 74 个公式耗时 |
| --- | --- | ---: |
| A1 | 原始 FP32 | 41.197 秒 |
| B1 | 候选 | 31.833 秒 |
| B2 | 候选 | 32.016 秒 |
| A2 | 原始 FP32 | 34.839 秒 |

- 平均耗时：38.018→31.924 秒，减少 16.0%。这包含此前外提重复投影的收益，不能全部归因于 FP16 存储。
- 进程 CPU 时间均值：493.516→425.914 秒。
- 独立公式进程峰值 working set 均值：1353.1→1192.5 MiB，低约 11.9%。
- 结束时 private commit 均值：1821.5→1697.0 MiB。

内存数字包括解释器、冻结输入、ORT 和 Session，并非仅权重。虽然文件减半，运行时恢复 FP32 计算，不能承诺内存也减半。原版两轮之间仍存在明显波动，不将其他时段的较慢结果用于宣称翻倍。

动态 batch=2 的两组对照通过，包括短长混合公式；原版与候选输出数组完全一致，形状分别为 `[2,53]`、`[2,151]`。

## 不同 PDF 的实际 Rust 验证

使用 `.venv` 已安装的 Rust 包，通过模型路径参数切换，串行解析 `demo/pdfs/demo1.pdf`。该文件的 56 个公式不同于冻结输入使用的 `03.pdf` 语料。

| 指标 | 原始模型 | 候选 |
| --- | ---: | ---: |
| 公式阶段，56 个公式 | 22.908 秒 | 20.902 秒 |
| 整份 PDF，含首次加载及相同导出 | 41.069 秒 | 38.194 秒 |
| 整个解析进程峰值 working set | 约 2806.9 MiB | 约 2657.8 MiB |

13 页结果通过既有参考校验：51140 个 Markdown 字符，Markdown、middle JSON、content list 一致，18 张图片的模式、尺寸、像素哈希一致。另直接比较了两次输出的 Markdown 字节和解析后的 JSON。

整份 PDF 本次耗时减少约 7.0%。这是单次串行对照，不是稳定性能保证，也没有实现全流程数倍加速。没有把只优化公式模型的结果扩展成所有模型、所有文档或整个安装包的压缩比例。

## 已排除的线索

- 大权重哈希审计未发现可直接去重的大块副本；不能把输入嵌入和词表输出矩阵当作同一权重合并。
- 对整数形状表达式进行保守折叠，在当前图没有找到额外可替换的常量。未声称获得新的解码图提速。
- 发现约 17870 个 FP32 次正规权重值，主要来自 BatchNorm 参数；单独测试 ORT 的 denormal-as-zero 后 74 个结果一致，但未观察到收益，未启用该选项。该选项会改变数值处理，且主线程设置涉及 Session 创建顺序，因此使用独立进程测试。[ORT 1.26.0 配置定义](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.26.0/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h)

后续若继续追求数倍提速，应评估重新导出或融合增量解码器，减少循环内的小算子执行；本轮没有证明现有模型可在保持识别结果的同时获得该幅度。继续扩大低精度量化范围目前不符合已测结果保持一致的要求。
