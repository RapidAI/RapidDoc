# Python API 兼容与自动加载（第 2 项）

最新交付：正式 `RapidDoc` 已改为共享 Rust 整份 PDF 引擎，分类/版面后处理和模型编排不再执行 Python 算法；新 release 已安装到现有 `.venv`，5 默认及 4 原生 API 案例严格对照通过。详细结果与剩余限制见 [Rust 核心交付记录](2026-10-28-native-api-core.md)。下文保留历次诊断记录，“待下沉/临时 Python”的旧状态以此条为准。

按原 `rapid_doc.main.RapidDoc/RapidDocOutput` 的 PDF 接口、默认配置、输入/返回/输出行为接入 Rust 包；本项完成后暂停给用户测试，不提前处理 PDFium 共存、印章或对比基准。

先解决已复现的文件预算和静默空结果，再接入自动运行库/模型定位、复用、原 auto 分类及进度日志。默认 V3、公式 M、OCRv6 与双模型表格参数按原源码，不能将原默认 auto 多边形悄悄降为矩形。

2026-10-28 用户纠正实现方向：分类、多边形和解析任务编排应进入可由其他语言直接调用的 Rust 核心；Python 仅保留原 API 参数、返回对象和回调的薄封装。已复制到 SDK 的 Python 算法文件是当前未验收的临时实现，应作为移植对照移出发布包，不能以拷贝 Python 规则代替 Rust 迁移完成。运行库/模型自动加载也应由统一 Rust 会话/文档入口管理，避免每种语言重复实现。保持原算法与严格参考，不能通过矩形替代、多字删减或参考改写缩小差异。

进度由核心结构化事件提供，默认英文阶段名/字段；交互终端提供可关闭、限频刷新的进度条，非交互日志仅保留开始/结束/警告/错误，不能每页每阶段输出一行中文。Rust 可使用 indicatif/tracing，跨语言绑定只转发事件。性能问题先记录：逐页反复打开 PDF、完整掩码/中间字符树经大 JSON 跨语言传输、任务收集与推理批次被拆散。页是识别单位，但要恢复原跨页任务收集/批处理；不能未经同条件测量就声称更快，也不能以无限并行换速度。

密集表格已修复原生分行、落格及字形容量不一致：完整页面沿用同一 vendor 内核，独立有界容量 100,000；小诊断默认限制不变。宿主保守工作量预算为 1,000,000,000，与文件级最大值一致，所有中间记录/输出仍受单独限制。单元格上下标处理仅传入本单元格 char_idx 所用的坐标映射，保留值及异常校验，避免重复拷贝整页映射和误触 20,000 限制。实际 20,198 字符文件的原生表格恢复专项通过；实际 API 的完整结果仍需严格对照原 Python 冻结参考，不能只看不抛异常。demo1 全文暴露的 LazySession 后置 OCR 类型校验未解包问题已修复，13 页完整 CPU 运行通过（51,140 个 Markdown 字符、18 个图片资产）；本次完整运行仅证明可完成，不能代替输出精度对照。第 2 项尚未完成，仍需 Rust 核心迁移、完整文件回归和用户测试。

进度显示已实现共享 `rapiddoc-core::progress::TerminalProgress`，Python 绑定仅转发阶段。自动检测交互 stderr，100 ms 限频、原位刷新，重定向日志默认不输出进度；`RAPIDDOC_PROGRESS=off/auto/always` 控制显示。兼容入口仅保留英文开始/结束 INFO，模型加载改为 DEBUG，失败保留阶段和页号。此处不宣称解析调度已经移入 Rust，现有临时 Python 算法仍待迁移。

多边形裁图遮罩进入 `rapiddoc-inference::crop_mask`，复用现有 OpenCV LINE_8 整数填充内核；保留 OCR 裁图先遮罩后白边、表格矩形裁图及公式扩展后丢弃多边形的原行为。Python 对照代码移到 `scripts/migration/references/polygon_crops.py`，不再打入 SDK。针对凹/自交/浮点/越界多边形与公式扩展的 36 组像素对照安装测试通过。

最终 release wheel 已安装现有 `.venv`（`build/wheels/rapid_doc_rust-0.1.0-cp310-abi3-win_amd64.whl`）。延迟识别器、原生进度、36 组裁图像素、4 页渲染像素、257 组适配器/8 页脱离句柄/13 个原生表格恢复正例及 2 篇 10 页宿主文档、兼容性审计回归通过，`pip check` 正常。实际默认 API 的 6 文件分类统计和 5 个文档案例全部通过，Markdown、JSON、图片像素严格匹配原 Python 参考：demo1 前 2 页 7,220 字符、密集表格 15,474 字符、small_ocr 首页 414 字符、03 首页 519 字符、论文模板首页 112 字符。扫描首个测试页已验收，不等于所有扫描件整文档质量普遍等价。

扫描渲染修复已加入 `render_model_page`：按原比例 cap 长边，不提高预算，也不盲目降低所有页面 DPI；实际比例随页面保存并用于 OCR、表格和组装。先在独立开发 wheel 验证，再统一更新正式包，避免定位中反复耗时 release 构建。开发包从 `build/api-dev-sdk` 加载，不作为用户日常测试解释器或正式运行库。

本轮最终安装/验证日志：`build/api-current-install.txt`、`build/api-current-documents-test.txt`、`build/api-current-{render_caps,polygon_crop,progress,lazy_post_ocr,native_host,compatibility}-test.txt`。未跑全量/CUDA，未改已有冻结参考；新增渲染参考使用独立原 Python 进程生成且禁止覆盖。

默认支持本机 CPU，与用户明确延期的 CUDA/增强阅读序分离。当前仅做 PDF/图像外层兼容，Office 未接前明确拒绝；未实现的可选配置明确报错，不能默默忽略。保持既有底层接口和冻结参考。

验收重点：实际 demo1 非空及原生失败可见、密集表格无丢字/截断、扫描件 auto OCR、默认模型路由与原版对照、路径/bytes/流/批量/页范围/输出字段/目录与 writer/data_uri、惰性加载和模型缓存、日志和失败定位。开发只跑受影响测试，阶段结束统一构建安装至现有 .venv，保留 build/migration 冻结数据。
