# 公式 ONNX 模型分析（2026-10-29）

本次仅分析，不修改模型权重、默认参数或已安装包，不构建 Rust。

## 分析对象

- 实际使用的 `pp_formulanet_plus_m.onnx`，593,908,338 字节（约 566 MiB）。
- SHA256：`52afa60ff51ad66cd7840a74188a058fe99081e617d3bd780117a2d67d94f50d`。
- 输入为 FP32 `[batch, 1, 384, 384]`，输出为生成的整数 token 序列。
- 使用 Paddle2ONNX 导出图，不能根据仓库内其他框架实现的代码猜测实际 ONNX 行为。
- ONNX Runtime 1.26.0，CPUExecutionProvider，图优化等级 ALL。
- 使用此前冻结的真实公式输入：短例输出 3 个 token，长例输出 151 个 token。预热一次，再分别跟踪短例、长例。

## 已确认的瓶颈和正常行为

### 1. 编码特征投影错误地放在了解码循环中

`Loop.0/body/MatMul.0` 的输入：

```text
外层图的图片特征 p2o.pd_op.transpose.0.0 [1,144,2048]
固定权重 linear_292.w_0 [2048,512]
```

随后 `Add.20` 加固定偏置。这两个节点都不依赖循环次数、当前 token 或 K/V 缓存。保守数据依赖分析在优化后的循环体内确认了这两个不变量节点；它们在 ORT 优化后仍留在循环中。

实际跟踪中，短例执行 2 次，长例执行 150 次，同一图片重复做相同投影。每次约 1.51 亿次乘加，长例本可省去其中 149 次，约 225 亿次乘加。这里的乘加次数是计算量，不是毫秒或预期提速比例。

这是当前最明确、最值得先验证的优化点：把原有 MatMul 和 Add 移到循环外，保留权重、输入尺寸和生成规则。仍须验证原始 token 一致性以及优化器融合是否改变浮点结果，不能仅凭数学等价承诺完全一致或大幅提速。

### 2. K/V 缓存正常，不是每步重算整个注意力历史

循环携带自注意力和交叉注意力缓存。长例中，第一层交叉注意力的 `MatMul.8`、`MatMul.9` 各执行 1 次，其余步骤走缓存分支。

词表输出层 `MatMul.85` 执行 150 次，但每次输入始终为 `[1,1,512]`，没有把完整历史 token 每次重新送入输出层。当前实际导出图是逐 token 解码；不能由其他实现里的并行解码参数推断这里一次生成多个 token。

### 3. 输出层本身较重

输出权重 `linear_231.w_0` 是 FP32 `[512,50000]`，约 97.7 MiB。每步对 5 万个词项打分，属于实际模型计算负担。另有同等大小的输入词嵌入；不能据此假定二者权重相同、能够直接合并。

这一部分受矩阵计算和内存访问影响，换调用语言不会自动消除。裁剪词表、量化、降低输入尺寸或限制生成长度都涉及精度或适用范围，本次没有采用。

### 4. 解码图存在大量小算子

优化前全图含子图共 2719 个节点，优化后 1224 个；优化后的循环体仍有 907 个节点，含大量 Shape、Slice、Unsqueeze、Reshape、Concat 等操作。

长例实际触发 137,534 次非控制流算子调用。这说明循环调度、动态形状处理和缓存整理值得继续分析，但这些节点并非全部多余，不能整体删除。

原图 1154 个 Identity 大部分已被优化掉，不能用原始节点数量声称它们都在反复执行。进一步简化或重新导出应基于优化后的图，并逐项验证缓存与动态 batch 行为。

## 验证及计时限制

- 预热、短例、长例的原始输出 token 均与此前冻结的 Rust 结果完全一致。
- 原模型没有被替换，生成的优化模型只保存在诊断目录中；它包含本机优化，不能直接作为通用发布模型。
- 本次启用逐算子 profiling，长例产生约 151 MiB 跟踪数据，带来明显额外开销。本次长例约 32.87 秒；此前同一输入未开启 profiling 的一次回放约 2.33 秒，运行条件也不同。**不能把本次跟踪耗时当成正常推理耗时，也不能直接用算子时间占比预测实际提速。**
- 统计非控制流算子时排除 Loop、If 等父节点，避免嵌套时间重复相加。执行次数和数据依赖比本次绝对耗时更适合作为结论依据。
