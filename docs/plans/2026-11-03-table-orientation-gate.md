# 表格方向模型触发优化

## 问题与修改

`page-dca64e05-1ce6-49ee-857a-9b5d05a87357.pdf` 的表格内容方向为 270°。原 Python 的生产裁图为 1000×2745，检测到 51 个文字框，其中 11 个高窄框（21.6%）。旧规则要求至少 3 个高窄框、比例至少 28%，因此未运行方向模型，直接保留 0°。独立运行模型得到 270°、分数 0.9035969。

本次独立 Python 与 Rust 同步修改：

- 保留 PDF 原生文字角度优先路径。
- 无原生角度、裁图高宽比大于 1.2 时运行方向模型；取消高窄框数量和比例的硬门槛。
- 表格模型建议为 90°/270°、得分至少 0.90，且领先次高类别至少 0.20 时才旋转；否则保留 0°。
- 方向分类一次返回标签、分数和次高分差，不增加第二次推理；模型继续缓存复用。
- 独立表格接口的方向处理也使用相同策略，不再单凭高窄框比例固定顺时针转 90°。
- `USE_DOC_ORIENTATION_CLASSIFY` 整页路径保留原有策略，没有套用表格置信度门槛。
- Rust 生产调度、原始 PNG 表格接口均在原生层执行相同选择策略。

门槛是本次小样本验证使用的保守值，并非完整评测确定的最优参数。不承诺消除所有误转；模型对裁图边界敏感，例如该文件保存的 998×2742 资产图只得到 0.879，而实际生产裁图得到 0.904。低分裁图仍保持原方向，不为单个文件降低门槛。

## 验证

- 81 项相关 Python 与安装后输出测试通过，另 7 项安装后原生方向策略测试通过。
- 目标 PDF 在两条完整 CPU 链路均转正；Rust 输出 19 行表格，包含正常横向的 `K. dubia`，没有开启整页方向分类或依赖文字回退。
- 7 张现有表格资产图的 Python/Rust 模型选择完全一致：3 张明显横躺窄表接受 270°；正常长表保留 0°，一张建议 90°但分数约 0.880 的长表被拦截。
- CPU Python 方向模型预热后，每张约 5–6 毫秒（7 张资产图各重复 3 次）。不含首次模型加载、完整 PDF 处理及转正后必要的 OCR 重检；不是整体解析提速结论。
- Rust `table_direction` 专项测试中 2 项独立测试通过；3 项旧参考/像素对照因 `build/migration/table-direction*.json` 已不在本机而未能执行。没有重写旧参考来充作通过。已用安装后原生合成策略测试和真实 PDF 验证本次行为。
- release wheel 已安装到项目 `.venv`。未跑全量文档或 CUDA。
