# DOC Python/Rust 性能与内存验收

此文保留优化前基线。后续功能、语料扩充及内存优化结果见 [DOC 收尾验收](2026-11-01-doc-completion-acceptance.md)，项目 `.venv` 已升级到该收尾版本。

本轮对已安装的 `office-doc-compat-20261101` 版本进行验收，未修改生产解析算法，也未重建 wheel。

## 结果

| 样本 | Python 热运行中位数 | Rust 热运行中位数 | 加速比 | Python 进程峰值工作集 | Rust 进程峰值工作集 |
|---|---:|---:|---:|---:|---:|
| 真实 docx_01.doc | 2.079 秒 | 0.353 秒 | 5.89 倍 | 332.5 MiB | 79.4 MiB |
| 生成的 6000 段纯文本 DOC | 1.376 秒 | 0.0646 秒 | 21.30 倍 | 348.0 MiB | 114.3 MiB |

真实样本冷解析：Python 2.371 秒，Rust 0.369 秒。导入与初始化另计，分别约 2.934 秒和 0.162 秒。

两份输入的完整 `middle_json`、Markdown、content list 和图片内容规范化快照哈希一致。图片仅在像素/SVG 内容一致后替换资产文件名，没有放宽文字、样式、链接、结构或块索引比较。真实文件为 3 个逻辑页、48 个资源。

真实样本的进程峰值工作集降低约 76.1%。此结果包含导入依赖，不能解释为解析算法自身节省 76.1% 内存。

## 内存口径与局限

两端导入后的工作集基线约为 Python 300.7 MiB、Rust 35.8 MiB。真实文件解析阶段采样到的新增工作集约为 Python 21.3 MiB、Rust 42.5 MiB；新增私有提交约为 Python 20.1 MiB、Rust 62.6 MiB。Rust 总进程内存更低，但本次并未达到“解析阶段新增内存也更少”的目标；基线加载、分配器复用和临时对象生命周期都可能影响这个增量，尚未进行原生分配归因。

内存由父进程读取子进程 Windows 计数器，目标间隔 2 毫秒，避免 Python GIL 阻碍同进程采样。仍有短峰漏采：例如 Rust 压力样本采样峰值只有约 89.5 MiB，而 Windows 保留的进程峰值为 114.3 MiB。因此上表采用操作系统保留的峰值，而不采用更低的采样峰值。该峰值也包含导入阶段，报告另存解析前峰值以供检查。私有提交不是实际物理驻留内存，不能与工作集混用。

当前只覆盖 1 份独立真实 DOC；6000 段输入是生成的重复文本，不代表复杂真实文档速度，也不代表 PDF 或其他 Office 格式的收益。

## 方法与复现

- Windows 11 26200，Python 3.14.5，系统报告 22 个逻辑 CPU。
- 两轮顺序独立进程，交换 Python/Rust 执行顺序；每轮一次冷调用和三次热调用，热中位数汇总六次调用。
- 耗时、冷解析内存、结果验证分别使用独立进程。输入先保存同一快照；计时包含完整公开解析和返回结果，但不含文件读取、导入初始化、验证和输出文件写入。
- 两端保持默认配置，不预加载 PDF/OCR 模型，不调整算法阈值或强制线程参数。
- 真实输入 SHA256：`6aae60b01f0e020c59d2299f217dbd5904df08182a31384db40953937f322fd1`。
- 已安装 `_native.pyd` SHA256：`b86a7f12ef17055f452c592748fead8a322da7f2c54e78d4b9c1e9fa2662b9e2`。本次指纹在测试后保存；期间未重装二进制，后续运行会在 manifest 中预先记录。

项目根目录运行（输出目录必须不存在）：

```powershell
.venv/Scripts/python.exe scripts/migration/accept_doc_performance.py --output build/doc-performance-new --rounds 2 --repeats 3 --stress-paragraphs 6000
```

已保存结果：`build/doc-performance-20261101/summary.json`、`reports.json`、`manifest.json`、每个 worker 的报告与日志，以及独立验证的完整快照。脚本支持 `--summarize` 从已有报告重建摘要，不重新解析。

后续优化优先分析 Rust 的临时文本映射、段落/表格中间结构、序列化及绑定返回对象的内存峰值。当前验收已证明该 DOC 路径速度和总进程内存优于 Python，无需为追求倍数改写解析规则或降低精度。
