# 融合后公式模型分析与交叉注意力缓存外提

## 结论

重新分析了当前保留的融合 M 候选，并测试将交叉注意力缓存完全外提。候选通过已测输出校验，但串行反向对照未显示新增速度收益，**不采用，不替换当前候选或默认模型**。

## 融合模型的新分析

对象：`build/formula-mha-half-20261029/formula-attention.onnx`，SHA256 `ee215a4db50b85bbfa3478ab81120bdb436beb3e86fd6f721b77effce53e871a`，ORT 1.26.0 CPU，自动线程、arena、ALL 图优化。

使用同一套冻结输入中的最短例（输出 3 个 token）和最长例（输出 151 个 token），另有一次短例预热。三次原始 token 均与原始 FP32 参考一致。只对少量代表输入启用算子 profiling，没有再次跟踪全部 PDF。

优化后的外层图 230 个节点、循环体 429 个节点；长例触发 65,836 次非控制流算子调用。此前未融合图的长例为 137,534 次，说明上一轮融合确实减少了算子调用，但调用数量不直接等于耗时比例。

| 代表输入 | 观察 |
| --- | --- |
| 最短例 | Conv 合计约 154 ms，为主要开销；只有两步解码 |
| 最长例 | 150 步解码；MatMul 合计约 922 ms，另有大量小算子、缓存和控制流开销 |
| 最长例的词表投影 | `MatMul.85` 执行 150 次，约 314 ms，是最大的单个节点 |

长例词表投影约占该次非控制流算子时间的 12.5%，并非绝大部分；也不能据此用量化输出层推断整个模型可以提速几倍。其余线性层及小算子分布在整个解码器中。短例与长例的瓶颈不同，不能只优化长例就推断所有公式都同比提速。

**这些毫秒包含 profiling 开销，仅用于定位。** 长例被跟踪的整次运行约 2.842 秒，非控制流算子累加约 2.519 秒。统计排除了 Loop、If 父节点，避免嵌套时间重复相加。不可与之前不同时间段的 profiling 绝对耗时比较，也不可把小算子的计时占比当成无 profiling 的精确性能分布。

## 交叉注意力缓存外提

原图每层只在第一步计算图片的交叉注意力 K/V，此后仍要经过 If 的缓存分支，并携带两个 K/V 状态。实验把 6 层共 12 个图片投影与缓存张量放到循环外，移除 6 个 If 以及 12 个循环携带值。

原有 MatMul、Add、权重、注意力掩码、词表和终止规则保留。只把缓存 reshape 改成 `[0,0,16,32]`，由 ONNX 的复制维度语义保留实际图片 batch 和序列长度，没有固定 batch 或图片内容。继续使用已验证的 FP16 存储、FP32 计算方式。

新工具 `scripts/migration/hoist_formula_cross_cache.py` 校验源模型哈希和目标子图结构，拒绝覆盖目录，生成独立模型并运行 ONNX checker。导出模型通过 74 个冻结公式的原始 token 校验，以及两组动态 batch=2 的完整数组对照，包括短长混合。

## 关闭 profiling 的速度对照

各轮使用独立进程，串行 A/B/B/A，相同输入、自动线程、arena 和图优化配置，进行相同短例预热。加载、输入读取及输出校验不计入推理耗时。A1 复用紧邻的标准 worker 报告，验证其模型哈希、线程、profiling 关闭等设置。所有 74 个原始 token 在全部轮次一致。

| 顺序 | 模型 | 74 个公式耗时 |
| --- | --- | ---: |
| A1 | 当前融合候选 | 31.317 秒 |
| B1 | 交叉缓存外提候选 | 30.482 秒 |
| B2 | 交叉缓存外提候选 | 35.138 秒 |
| A2 | 当前融合候选 | 30.137 秒 |

平均 A=30.727 秒，B=32.810 秒，候选平均约慢 6.8%。运行存在波动，不能证明它每次都更慢，但没有足够证据支持采用。最初单轮 29.955 秒也未作为提速结论。由于未显示收益，本轮未进一步跑 PDF 或全量回归。

## 后续边界

本轮没有找到新的可采用的提速点。词表投影仍较重，但并非单一主导热点；小型缓存改图再次未显示稳定收益。若继续追求大幅提升，需要更完整地评估解码执行结构、运行库内核或重新导出方案，不能仅从节点数量承诺倍率。压缩或改精度的路线仍须独立评估，不能把改变输出的候选当作无损优化。
