# 正式解析容量限制清理

## 原则

正常解析不使用 Rust 移植时额外添加的字符、条目和累计工作量上限。显式诊断预算、结构合法性、内存尺寸溢出检查及 Python 原有算法阈值分别处理，不能通过截断内容或吞掉异常让文档“成功”。

## 本次变更

- 原生文字源、文字噪声、图片区域、栅格图、堆叠图、行内证据/输出、表格块的 8 个数组检查函数接入已有正式解析策略：记录数量不再受固定上限约束；坐标、颜色等定长数组检查保留。
- 表格文字聚类和行列推断中的 512/4096 行、1500/20000 字符记录限制同步处理，包括借用入口。
- 原生字符记录和文字签名的 256 字节上限在正式流程中停用，字符串类型检查保留。
- 补齐表格文字度量及引擎策略辅助数组的数量检查遗漏。
- 诊断入口仍保留原有限制；作用域退出后恢复。用户显式设置的 JSON、输出和工作量预算继续有效。

## 对照与保留

- Python `_collect_document_sources` 没有上述数组长度上限。
- Python `_table_recovery/vector.py` 定义 `MAX_TRACKS_PER_AXIS = 200`，Rust 对应表格轴线拒绝条件保留，属于算法候选筛选。
- Python `engine.py` 的相交图元计数及 `vector.py` 的精确片段计数以 5000 为候选筛选条件。修正此前错误套用无限预算策略的 3 处判定；只拒绝该候选，不报整份文档资源错误。
- Python Office `limits.py` 已有单项 128 MiB、累计 512 MiB、网格槽位和记录深度等限制，Rust 对应行为保留。
- 坐标必须为有限数、数组结构/索引正确、尺寸乘加不可溢出等检查保留。大坐标值的额外保护及未迁移功能的 Unsupported 不属于本次数量限制修复，不能宣称所有 Rust/Python 异常行为已完全一致。

## Java 包装层

`parseSource` 中的原生调用、DocumentResult 包装及可选 `writeTo` 为 Java API 适配；解析与下载在 Rust。Java 文件输出失败继续报告 IOException 对应错误，不应静默返回已写出。无需为了减少 Java 行数把整个适配层搬入 Rust。

## 验证

仅运行受影响文字、图形、表格组装测试及真实触发 PDF 的纯规则路径。完成后统一构建并更新本机绑定，避免多次重复打包。未进行全量文档或 CUDA 验收。

清理限制后，真实触发文件暴露普通横线候选的重复复制：候选行改用 Arc 共享；同横向区域裁剪结果按 Python 思路缓存。候选顺序和几何判定不变；显式有限工作预算仍走原计数路径。开发验证进程曾因内存持续增长被手动停止，属于测试执行边界，没有加入生产文档容量上限。

首轮交付记录（最新结果见文末）：

- 密集源记录、密集文字聚类、显式预算恢复、Python 图元候选门测试通过；现有真实表格冻结参考、完整页面收尾和上游 PDF 对照通过。
- 本机 Python 七格式 URL/字节对照和生命周期通过；Go 测试、Node 11 项通过。Java 集成回归结果见 `build/release/capacity-delivered-java-tests.log`。
- 实际 HTTPS PDF 的纯规则路径不再立即触发原 5000 项错误，但最终版本未在 60 秒开发验证窗口内完成，已停止该测试进程。不能宣称该文件纯规则端到端验收通过；候选枚举耗时仍待继续优化。该 60 秒没有写入 SDK。
- `.venv` 已更新原生扩展，Java 两个 Maven 仓库已同步校验，Go/Node 手动示例已切换 `capacity-delivery` 原生包。未发布远端包。


## 密集横线候选性能修复

本轮对照同一页的原始输入：6555 个文字片段、171 行、130 条规则线，其中一组有 122 条横线。完整枚举 7381 个边界组合后，Python 与 Rust 均接受 7216 个草稿；不通过降低候选数量或增加超时上限提速。

- 对齐 Python 的稳定列聚类结果/前缀缓存与分带二分索引，保持边界上的行同时属于相邻两带。
- 缓存横向裁剪行时，单独保留原行范围及排除片段前的中心位置，用它们判断纵向准入；排除后的几何仍用于后续判定。
- 草稿按页面内行身份共享不可变 Rust Row；生产物化直接借用核心行，不再逐候选执行 Row→JSON→Row。
- 物化复用已解析的页面行和借用的原始文字源；同页、同横向走廊的表注字号/字体/标记特征缓存复用，归属仍逐候选计算。规则展开、表题及表注沿用同一算法。
- 生产路径按稳定评分顺序逐个物化、合并，及时释放中间候选；共用原候选合并函数，保持注释和完整表优先规则。显式有限工作预算继续使用原路径。

复现工具：库内忽略测试 `external_rule_page_profile`；`RAPIDDOC_RULE_PDF` 指向外部 PDF，`RAPIDDOC_RULE_CAPTURE` 可捕获候选输入（仅测试构建），`RAPIDDOC_RULE_REPLAY` 可复放候选阶段。`RAPIDDOC_NATIVE_PROFILE=1` 输出阶段耗时，默认关闭。真实 PDF、捕获输入及探测脚本放在已忽略的 `build/capacity-regression`、`build/`，不作为包运行依赖。

冲突筛选的生产入口借用候选投影且只返回排除索引；筛选结束即释放草稿成员投影，避免在整个物化循环中同时驻留多份大 JSON。


### 追加验证中的遗漏

触发页完成表格处理后，正式路径在上下标几何中遇到未套用资源策略的 `Context::rows(max_chars)`。该检查直接使用 1500/20000 诊断值，现接入共享 `resources::limit`，同时处理单条字符记录 256 字节检查。新增 20001 条记录回归，覆盖兼容作用域及退出恢复。

连通网格框及其成员集合按单页物化上下文缓存。缓存键使用精确浮点位，成员集合与每个候选原核心合并后，仍逐项排除其注释成员。表注缓存同样仅限当前页和当前角度。


### 候选成员直接传递

生产物化新增类型化入口，核心准备直接返回几何、表题及 Arc 共享成员集合。表注收集借用核心成员，避免每个候选的成员集合经过 JSON 编码、解码。网格扩展结果共享不可变成员集合，相同集合的候选合并直接复用。最终候选输出仍统一经过原候选输出函数，原注释仲裁共用同一实现。

诊断入口保留原 JSON 参数与有限预算语义。类型化物化与原入口逐候选对照通过，同时通过真实表格冻结参考、完整页面收尾及上游 PDF 回归。性能复测逐字比较优化前 Rust 的 HTML 输出。此前 Python `table_enable=False` 基准输出为图片，不能据此声称 Python/Rust Markdown 完全一致。


### 与原版 5.33 秒基准的核对

用户在 DocVortex 公开 `parse → export → save_bundle` 流程测得 `49－长表格-密集型.pdf` 总耗时 5.33 秒。该文件与 URL 下载样本的 SHA-256 均为 `1BBD28A4F0733AB3DBD7E651AFED11338E8BAF535AD92413D96B108EAB5A76ED`，属于同一个 PDF。原版具备表注标记命中复用、正文高度预处理、共享核心成员及原生合并。此前把 Rust 120 秒简单归因于纯规则配置不足以解释差距。

本轮追加表注标记已知命中和逐来源判定缓存、正文高度数值缓存及按标记存在性跳过无效扫描。表注选择保留核心集合借用，只记录新增成员。核心成员通过批量构建保留排序、去重语义。缓存仅在单页物化上下文中使用，显式有限预算入口沿用原路径。

- 同一真实 PDF，纯规则配置、公式/模型表格关闭，完整解析实测从约 120.74 秒降至 **33.11 秒**。候选物化约 103.30 秒降至 **14.14 秒**，候选枚举 **0.31 秒**。输出 **15478 个 Markdown 字符**，与优化前 Rust 的完整 HTML 输出逐字相同。

- 仍未达到用户原版 DocVortex 的 **5.33 秒**。当前主要剩余耗时为候选物化约 **14.14 秒**、页面源准备约 **6.68 秒**，另有表格认领及页面处理。不能宣称本轮已达到原版性能。

### 原版 4.57 秒差距的实测核对

使用用户同一 Python 3.12 解释器，实际导入 site-packages/docvortex，对同一密集 PDF 按公开 parse/export/save_bundle 流程计时。仅给选定函数包裹 perf_counter（不启用 cProfile）的本次总耗时 **4.63 秒**，与用户 4.57 秒接近。另存 cProfile 供调用次数排查，其约 9 秒包含分析器开销，不作性能基准。

- 原版生成约 7216 个草稿，扩展/表注调用各 7217 次，和 Rust 枚举规模一致，差距不是原版少处理几千候选。
- 原版候选检测 **1.625 秒**，其中原生合并/候选扩展链 **0.948 秒**；Rust 候选检测 **7.812 秒**，其中物化约 **4.740 秒**。这些是包含关系，不能相加。
- 原版表格恢复/物化 **0.266 秒**，Rust 表格认领及恢复提交 **1.682 秒**；阶段范围并非完全相同，作为链路差距证据而非严格同一函数对比。
- 原版来源采集 **0.392 秒**，Rust 原生页面采集 **1.384 秒**，两者范围也存在适配层差别。
- 原版同样调用 Rust 原生扩展。其 _NativeCoreLineSet、PreparedRuleCandidates 和 NativeTableGrid 将核心及网格成员驻留于原生共享结构，最终保留候选才导出。当前移植虽然已有行位集合及 Arc 优化，仍逐候选导出为完整 BTreeSet，并将阶段资料放入通用 JSON Value；还未对齐上游的紧凑成员和连续处理数据流。这是仍慢的重要实现差异，不能归因为 Rust 语言或 ORT。
- 原版 Markdown 9562 字符，Rust HTML 表格 15478 字符，格式不同；按表格解析后 **121 行、847 个单元格内容一致**。此前与旧 Rust 逐字一致只验证未回退，不能替代上游对照。

本轮只做原因定位，未另行更改生产算法。后续应集中对齐紧凑成员和表格恢复链，避免继续仅用零散缓存追速度。测量及对照文件放在已忽略的 build/capacity-regression/upstream-timed、upstream-profile；日志 build/release/upstream-457-*。


### RapidDoc Python 与独立 DocVortex 的后端差异

用户新日志：论文模板 RapidDoc Python 12.20 秒、Rust 8.52 秒；密集表格 Python 19.16 秒、Rust 14.04 秒。当前两份 demo 均配置 docvortex_rule，不能把日志中的 Layout Predict 耗时直接当成版面模型推理。

进一步代码与运行时确认：内嵌 rapid_doc._vendor.docvortex_core._compute_backend.get_native() 固定返回 None，backend_info() 实际输出 backend=python、extension=None；用户 Python 3.12 独立 DocVortex 则加载 docvortex._native 协议 43。内嵌候选 merge_owned 在 native=None 时返回参考路径，因此没有享受独立 DocVortex 的原生扩展加速。这解释了 RapidDoc Python 与独立上游的重要性能差距，不能仅归因为额外 OCR/公式处理。

RapidDoc 的管线确实还在 analyze_docvortex_layout 后渲染页面、获取文字/图片字典，并进入模型补充、组装输出。但本次密集表格从 22:09:42.267 到 22:10:00.811（Batch）约 18.54 秒已经发生在后续批次模型处理之前；模型检测与收尾只有约 0.44 秒，且 Table Predict 为 0 项，不能把约 19 秒主要归到表格模型推理。Rust 类似，13.57 秒 Layout Predict 覆盖原生分析，统计中的 layout=0 也不能说明原生分析没有耗时。

后续 Python 性能任务需单独审查嵌入式原生后端的接入与打包，不应只把 None 改成任意全局 docvortex._native 导入：模块类型、协议、适配语义及 PDFium 共存均需验证。本条只记录分析结论，未修改后端默认行为。


### 对齐共享成员、字符准备与表注几何

本轮改造 Rust 原生候选的连续数据流，不改变模型、阈值、候选枚举、完整表保护及注释仲裁：

1. 新增内部 table_members::Members，以单页排序编号域和共享位集合保存核心/网格成员；核心准备、表注包含查询、网格并集、注释排除、候选合并均保持紧凑表示，最终输出才展开编号。跨编号域或特殊来源使用精确树集合回退，不新增不支持错误。Arc 写时复制保证候选和缓存互不污染。
2. 表注标记的字符几何、Unicode 归一化和短文本词元按单页预处理复用。上标匹配和短文本规则沿用原实现，增加旋转/全角等对照。
3. 表注几何按不可变行序列及实际排除成员复用。选择规则仍完整执行；缓存沿用上游 128 项/16384 权重约束，满后只重算，不限制输入或删除候选。新增相同行、不同核心排除成员回归。

同一密集 PDF、同一纯规则基准，独立进程实测 **15.12 → 13.40 秒**，候选物化 **4.74 → 3.55 秒**，候选检测 **7.81 → 6.53 秒**，表格恢复相关提交 **1.51 秒**。峰值工作集 **1357611008 字节（约 1.26 GiB）**，并未明显降低。中间共享集合版本 14.06 秒，加入字符准备复用 13.54 秒，最终 13.40 秒；均属于单次运行记录，不能将每个小差异视为稳定收益。
