# DOCX 效果、速度和内存验收

当前已安装 `.venv` 中的 `rapid_doc_rust.RapidDoc` 与本地原 `rapid_doc.RapidDoc` 对比。8 份本地 DOCX（含零字节空文档）和 1 份把现有 test.docx 正文重复 25 次的压力文档，两轮独立进程反序执行，全部成功，Markdown、中间 JSON、content_list 及图片内容全部一致。

本次范围的 DOCX 阶段验收通过，可以继续 XLSX；未发现需要先回滚或优化的明显性能差距。不将此结论扩展到所有客户端文档、少见编码或跨平台。

## 测量口径

- 两套公开 API 均使用默认配置，不预加载模型、不关闭解析功能，不写导出文件。
- 每轮/每个文件/每套引擎使用独立进程；两个轮次交换 Python/Rust 执行顺序，串行运行。
- 导入及 engine 初始化单独计时。每个进程先测一次首次解析，再测 3 次复用 engine 的解析；下表为两轮共 6 次复用解析的中位数。计时不包含参考比较、图片校验和文件输出。
- 内存使用 Windows OS 进程峰值和另一次独立解析的 2 ms 采样。OS 峰值在校验图片/序列化快照之前采集，含导入和此前解析；解析阶段采样峰值另存，短暂尖峰可能遗漏。两套公开入口的导入依赖不同，原 Python 基线约 298 MiB，Rust 约 34 MiB，不能把全部内存差都解释为 Rust 核心算法节省。
- 图片先按尺寸/解码 RGBA/SVG 结构和嵌入像素核对，再用内容标识替换文件名比较引用；保留已记录的 PNG 编码/哈希命名差异，没有放宽文字、结构或像素一致性。

## 复现和保留结果

```powershell
.venv/Scripts/python.exe scripts/migration/accept_docx_delivery.py --output build/docx-acceptance-new
```

脚本只生成独立压力测试文件和报告，不修改真实输入或生产解析器。默认生成目录必须不存在，避免覆盖旧测量。当前结果在 `build/docx-acceptance-20261031/`：

- `manifest.json`：解释器、平台、CPU 数、输入字节/SHA256、轮次及复测配置。
- `reports.json`：36 个独立进程，包含首次/复用耗时、基线、OS 峰值、采样峰值和可用物理内存。
- `summary.json`：逐文件比较、效果一致性、速度比和内存比。
- 每个 worker 的 `snapshot.json`、`report.json` 和日志。

未执行全量 PDF/CUDA，本轮没有改变 DOCX 算法、重新安装运行库或为了速度调整精度。DOCX 原有 353 份冻结参考和安装验收仍由前一阶段记录补充；少见图片编码、跨平台和更广泛异常文档继续列为后续专项。

后续顺序：XLSX → XLS → PPTX → PPT → DOC。电子表格图表内的工作簿读路径不等于完整 XLSX 转换器，当前先把原 SpreadsheetProjector 的共享规则接入 Rust。
