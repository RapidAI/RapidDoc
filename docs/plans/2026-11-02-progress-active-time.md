# Rust 进度条阶段计时

> 后续修正：下面的“累计工作时间用于进度条”方案已撤回。它造成方向条
> 实际挂起十几秒而显示不足一秒，混淆 tqdm 的 elapsed 含义。当前进度条
> 统一显示真实经过时间、墙钟速率与 ETA；原生累计工作时间保留为单独汇总。
> 页面执行顺序未改，因此方向/版面条同时跨越同一段等待时间是正常的，
> 不应相加为总耗时，也不应拿进度条速率比较模型推理性能。

当前安装包：`build/progress-wall-clock-windows-wheels/`。此次直接复用
原生显示组件，只调整兼容层事件转交和汇总，Rust 构建步骤 1.79 秒。
七项回归通过，验证生产 API 进度条不传入累计处理时间、两个窗口的
累计处理耗时正确求和，以及既有 IDE/重定向/关闭/绘图警告与错误日志。
真实 14 页完整 snapshot 与之前精确一致；日志见
`build/progress-wall-clock-smoke.log`，阶段汇总明确注明排除了交替阶段和
模型加载。模型初始化仍独立报告，总完成耗时仍含全部工作。

以下保留前次方案记录，累计时间采集仍使用，但不再作为进度条时钟。

## 原因

原生流水线按页交替渲染、方向判断和版面识别。旧进度条从第一次显示
开始累计墙钟时间，方向条把中间的版面、渲染、模型初始化都算进去。
同一份 14 页文件曾显示方向约 11 秒，而内部方向阶段含加载仅 0.697 秒。
这属于显示统计错误，不能用来比较 Python/Rust 的方向推理性能。

## 修改

- Rust 生产事件新增可选 `elapsed_seconds`，由实际工作边界累计，
  Python 仅传递给原生显示层；旧的三参数进度 API 保持可用。
- 方向、版面、OCR 检测、公式、OCR 识别、表格、印章和组装的进度
  使用各自处理时间，跨窗口从零累计，不混入其他阶段的空档。
- 模型注册表统计描述符解析、模型校验和会话加载时间；阶段计时
  扣除本阶段发生的这些初始化耗时。初始化总时间单独报告。
- 速率、已用时间和 ETA 使用同一处理时间来源；总完成耗时仍为完整
  墙钟时间，包含初始化、渲染、写出等全部工作。
- 不调整模型、输入、batch_size、调度顺序、阈值、排序或解码。

原始细分性能诊断项有各自范围，不能直接把所有项相加为总耗时；
部分为父子阶段。此次主要修正用户看到的进度条统计，不代表推理提速。

## 验证

编译检查通过。回归包含：在方向条更新之间插入 100 秒的其他阶段
计时，方向完成时间仍为显式提供的 0.35 秒，14 项速率为 40 it/s；
负数和 NaN/Inf 时间拒绝。沿用终端/IDE/重定向、关闭显示及绘图日志
的既有定向回归。

## 本机结果

Windows release wheel 已安装项目 `.venv`，`pip check` 通过。
六项日志回归和原生格式测试通过。实际 14 页测试中：方向累计
1.141 秒，进度条 14/14、12.26 it/s，与内部计时一致；版面处理
17.466 秒和模型初始化合计 3.592 秒均未计入方向条。

完整 14 页输出与修改前精确一致；另测论文两页的 5 个公式及一页
长表格，两组完整 snapshot 也与修改前一致，覆盖窗口重置和不同模型。
snapshot 包括 Markdown、中间结构、内容列表及资产像素。真实耗时
受机器负载影响，此测试用于验证统计范围，不作为 Python/Rust 速度结论。
ETA 表示剩余的本阶段工作时间，不包含将来穿插执行的其他阶段。
