## 已定位的性能差别与剩余工作

- 首轮 Python 默认使用已有自定义 CUDA 算子、部分模型图重写和版面 IO Binding，Rust 当时使用原始 ONNX 图，GPU 执行路径未完全对齐。后续对齐进展见第二阶段。没有修改权重、降精度或使用特定文档补丁。
- 关闭 Python 的上述优化做原始 ONNX 对照后，两页扫描复用耗时从 0.936 秒变为 2.319 秒，仍快于 Rust 的 6.643 秒；论文为 0.583 秒，仍快于 Rust 的 1.131 秒。原始 ONNX 对照仍有数值快照差异。因此自定义算子差别只能解释部分差距，不能当成全部根因。
- Rust OCR 检测增加可选 `RAPIDDOC_CUDA_PROFILE` 分段计时。两次扫描共 40 次检测调用：准备 0.057 秒、推理调用 10.771 秒、后处理 0.047 秒。主要差距在推理调用内部。同形状连续调用很快，形状变化常有明显开销；是否来自卷积调优、会话重建或批次策略还需进一步隔离，尚无定论。
- Python GPU 检测有同尺寸分组，Rust 当前按页、按块调用，需对齐批次与会话复用行为。把双方线程数改为 1 未解决扫描性能差距；Python 重复运行的论文快照完全一致。
- 下一阶段应先检查 GPU 会话生命周期、动态尺寸与批次行为，再评估 Rust 接入已有自定义 CUDA 算子及共享模型图准备方式，并复核坐标、置信度差异。不得直接放宽断言后宣称验收通过。
- 多 GPU、长文档显存峰值、更多样例回归及稳定重复基准尚未验收。当前显存记录为解析后的进程分配，不是峰值；Linux wheel 暂依赖环境提供 PDFium/GEOS 路径，不是独立发行包验收。

## CUDA 执行路径对齐与提速（第二阶段）

已确认独立复现：同一个原始 OCR 检测模型、同一个 ORT 运行库，交替输入不同尺寸时，Python 与 Rust 都反复出现约 0.18～0.33 秒的推理开销。不是仅 Rust 的序列化或前后处理问题。Python 已有 CachedConv2D 的按尺寸缓存路径没有被迁入 Rust，这部分执行路径差异是首要修复对象。

实现：

- Rust 模型描述符增加 `operator_libraries`，由 Rust 注册已有 CUDA 算子库；库路径纳入会话缓存键，注册失败正常报错。直接使用 Rust 或其他绑定也可以提供同一描述符，不依赖逐页 Python 回调。
- `scripts/migration/prepare_cuda_models.py` 在模型准备阶段复用项目已有图重写代码，生成独立 ONNX 和 SHA 清单。原模型和权重保持不动，页面解析过程中不执行 Python 图重写。
- 可选 `--compact-ctc` 与 Python 已有 GPU ArgMax/ReduceMax 路径对齐，只传回时间步索引、FP32 分数；Rust 使用与完整概率表相同的 CTC 字符去重和置信度计算。含重复、blank、相同最大值、异常索引、非有限分数及形状错误的测试通过。
- 可选 `--compact-layout` 与 Python 已有二值版面掩码 uint8 路径对齐，只有证明为比较运算产生的 0/1 输出才允许转换；不截断概率掩码。Rust 原生支持 uint8 张量及原有多边形后处理。rect/poly/quad 的 int32/uint8 等价测试通过。
- `RAPIDDOC_CUDA_MODEL_MANIFEST` 显式指定已准备清单；源模型、准备图和算子库均校验 SHA，CPU 请求忽略此 CUDA 清单。当前仍为隔离验证配置，未把实验图或 Linux wheel 安装进用户 Windows `.venv`。

阶段验证：CachedConv 后 6 组全部通过，Markdown/图片一致；继续紧凑 CTC 后 6 组完整快照与 CachedConv 版完全一致。两页 CPU 论文与原 Python 完整快照一致。6 项配置检查、5 项 Rust 参数/库检查、3 项 CTC 集成检查、2 项原 CTC 解码检查及 1 项真实 CPU 会话缓存检查通过。

额外尝试运行历史 `raw_recognition` 检查失败：当前磁盘缺少其 `build/migration` 输入夹具，另一个一次性计时测试因历史输出文件已存在而失败；没有删除旧记录或将其计入通过数量。CPU 实际模型解析及上述受影响检查已单独验证。

## 第三阶段：OCR 裁图插值复用

进一步实测发现 GPU IO Binding 对现有 Rust 路径没有稳定收益：论文、扫描、印章的完整快照一致，但复用中位数约为 0.280、0.822、0.651 秒，与第二阶段结果接近，实验实现已移除，没有增加新的默认开关。三通道 SIMD 实验在内核测试中只有约 7% 收益，也未保留。

实际保留的优化位于 `rust/rapiddoc-inference/src/image/crop.rs`：

- 对精确轴对齐的变换（交叉项和透视项均为 0），三次插值可以分为水平、垂直两部分。原实现对每个输出像素重新计算四行水平插值；现在缓存最多四行结果供相邻输出行复用。
- 每一通道的 FP32 tap/FMA 累加顺序、最终 ties-even 舍入、边界复制、旋转规则保持原样，没有近似系数、量化或降低输出分辨率。倾斜或透视变换仍走原来的通用内核；不支持硬件 FMA 的平台继续走原路径。
- 使用 256 像素宽的分块处理，临时系数和行缓存约 24 KiB（64 位环境），不随整个文档页数或裁图宽度增长，不增加输入拒绝条件。

256 组单像素、小图、边界、缩放和反向坐标逐像素比较通过，另有 255/256/257/1025 宽度的分块边界检查。release 内核交替测量：原路径中位数 2.079 毫秒，新路径 0.470 毫秒，约 4.4 倍；这是单独内核收益，不能当作整篇 PDF 的加速倍数。2 项裁图错误行为、3 项 CTC、5 项模型参数/库检查、1 项真实 CPU 会话缓存、6 项 Python 配置检查通过。

## 第四阶段：定位并修复 CUDA 依赖库差异

对同一 RGB 图像、同一前处理、同一 ONNX 图逐层对照：前处理张量逐位一致；同一独立推理环境中，Python ORT 与 Rust ORT 的原始框输出也逐位一致，矩形后处理一致。图输出名称、CPU arena 和 IO Binding 对照没有解释完整 Python 流程中的差异。

通过 `/proc/self/maps` 确认实际依赖库不同：

- 完整 Python 流程加载虚拟环境的 NVIDIA pip 库：cuBLAS 12.4.5.8、CUDA Runtime 12.4.127、cuDNN 9.1.0.70。
- 原 Rust 路径依赖系统动态加载：cuBLAS 12.2.1.16、CUDA Runtime 12.2.53、cuDNN 9.10.2。相同 ORT 版本和模型 SHA 并不代表相同底层计算环境。

独立推理预加载相同 NVIDIA 库后，论文版面原始输出与完整 Python 流程逐位一致，两页论文完整解析快照完全一致。说明该组坐标/分数差异来自运行库组合，不是靠截断小数、放宽容差或改权重修复。

修复在 `bindings/python/python/rapid_doc_rust/_runtime.py`：首次解析 CUDA 模型描述符或创建 CUDA 会话前，调用 ORT 官方 `preload_dlls(directory='')`，优先加载当前环境的 NVIDIA 库；通过进程内锁和成功标记只执行一次。CPU 路径不调用，不额外导入 PyTorch；失败不会标记成功或静默继续。原生模型算法和 Rust CUDA 执行仍保留在 Rust。

验收 worker 新增实际已加载 cuBLAS/cuDNN/CUDA Runtime 库路径记录，后续对照同时检查这组路径，避免只比较 ORT 版本。8 项配置、缓存、预加载次数及失败重试检查通过。
